# Формат файла стиля для SRA (Software-based Real-time Arranger)

> **Внимание.** Этот документ описывает формат, который понимает **форк SRA**,
> поддерживаемый Alexander Tesanov. В этом форке внутренняя раскладка
> MIDI-каналов **сдвинута** относительно оригинального проекта ZZ-Denis.
> Файлы стилей, созданные для оригинального SRA, **не загрузятся без
> миграции** (см. раздел 4.3).

## 1. Общие сведения

Файл стиля SRA — это **стандартный MIDI-файл формата SMF Format 0** (не Format 1).
Файлы называются `style0.mid` … `style127.mid` и размещаются либо в той же
директории, что и исполняемый файл SRA, либо в каталоге, заданном
параметром `--styles-dir PATH` (командная строка) или ключом
`styles_dir = PATH` (конфиг-файл).  Если ни то, ни другое не задано,
SRA ищет стили в текущем рабочем каталоге.

Все параметры и музыкальные данные находятся в **одном треке** (`MTrk`).
Формат 0 означает, что все MIDI-каналы пишутся в одну дорожку, а не разбиваются по трекам.

> **Важное предупреждение.** SRA — не универсальный MIDI-плеер. Парсер
> style-файлов в `libsracore` рассчитан на **строго определённую байтовую
> структуру**, которая получается при экспорте из большинства DAW с
> включённым running status. Файлы, экспортированные иначе (в частности,
> с отключённым running status в первом такте), могут читаться
> неправильно — вплоть до ошибки `Error(3)` или загрузки мусорных
> параметров. Детали — в разделе 4.4.

> **Второе важное предупреждение.** SRA читает delta только как
> **1- или 2-байтовый VLQ**. Значения delta ≥ 16384 (то есть требующие
> 3-байтового VLQ) приводят к **потере синхронизации** и падению
> с `SIGSEGV`. Это накладывает жёсткие ограничения на PPQ и длину
> секций.  Детали — в разделе 4.6.

---

## 2. Структура файла

```text
MThd (заголовок, 14 байт)
MTrk (единственный трек, переменная длина)
├── Такт 1 (служебный): 5 параметров + служебные события
├── Такт 2 и далее: музыкальные данные
│   ├── Блок для аккорда C   (IL + ML_A + 1 + ML_B + 1 + EL тактов)
│   ├── Блок для аккорда Cm  (то же количество тактов)
│   └── Блок для аккорда C7  (то же количество тактов)
└── Meta:EndOfTrack
```

## 3. Первый (служебный) такт

Первый такт содержит **служебное Meta-событие формата v2**, из которого
SRA считывает все параметры стиля при загрузке.  Служебные NoteOn-события,
которые использовались в старом формате, **больше не поддерживаются**.

### 3.1. Meta-событие v2

Параметры кодируются одним Sequencer-Specific Meta-событием:

```
FF 7F 0B BE EF 01 <tempo> <beat> <tt_hi> <tt_lo> <il> <ml_a> <ml_b> <el>
```

Разбор по байтам:

| Байт | Поле | Значение |
| :--- | :--- | :--- |
| `FF 7F` | Meta-заголовок | Sequencer-Specific Meta |
| `0B` | length | длина полезной нагрузки = 11 байт |
| `BE EF` | сигнатура | «наша» метка SRA |
| `01` | версия | версия формата (сейчас — 1) |
| `<tempo>` | Tempo | 10–125, **половина BPM** (итоговый темп × 2 = 20–250) |
| `<beat>` | Beat | 2, 3, 4 или 6 — число долей в такте |
| `<tt_hi>` `<tt_lo>` | t_time | длина такта в тиках, 2-байтовый 7-битный VLQ (0–16383) |
| `<il>` | IL | 1–32 — число тактов во вступлении |
| `<ml_a>` | ML_A | 1–32 — число тактов в **Original** |
| `<ml_b>` | ML_B | 1–32 — число тактов в **Variation** |
| `<el>` | EL | 1–32 — число тактов в концовке |

> **Темп вводится вполовину.**  Как и в старом формате, значение `<tempo>`
> — это половина фактического BPM (для 120 BPM → 60).  SRA умножает его
> на 2 при загрузке.  `Meta:SetTempo`, если он есть, **игнорируется** —
> темп берётся только из этого поля.

> **`t_time` хранится явно.**  В отличие от старого формата (где длина такта
> вычислялась из delta первого события тела), в v2 `t_time` — это отдельное
> поле в Meta.  Именно оно определяет длину такта при воспроизведении.
> Обычно `t_time = 120 × beat` (при PPQ = 120), но это не обязательно —
> главное, чтобы `t_time × SESSION_MAX` укладывалось в 2-байтовый VLQ
> (см. раздел 4.6).

> **Верхняя граница IL / ML_A / ML_B / EL — 32.**  Ограничение связано
> с внутренними массивами движка:
> `sty_session_init[3][6][SESSION_MAX][...]`, где `SESSION_MAX = 32`.
> При попытке загрузить стиль с бо́льшим значением `parse_style_header`
> вернёт `Error(3)`.  Практический предел 32 также гарантирует, что
> `t_time × SESSION_MAX` укладывается в 2-байтовый VLQ (лимит 16383).

### 3.2. Пример байтового дампа

Ниже — Meta-событие из `tools/make_test_style_v2.py` при
`tempo=47, beat=4, il=4, ml_a=4, ml_b=8, el=4`:

```text
00 FF 7F 0B BE EF 01 2F 04 03 60 04 04 08 04
│  │  │  │  │  │  │  │  │  │  │  │  │  │  │
│  │  │  │  │  │  │  │  │  │  │  │  │  │  └─ el=4
│  │  │  │  │  │  │  │  │  │  │  │  │  └──── ml_b=8
│  │  │  │  │  │  │  │  │  │  │  │  └─────── ml_a=4
│  │  │  │  │  │  │  │  │  │  │  └────────── il=4
│  │  │  │  │  │  │  │  │  │  └───────────── t_time lo=0x60
│  │  │  │  │  │  │  │  │  └──────────────── t_time hi=0x03
│  │  │  │  │  │  │  │  └─────────────────── beat=4
│  │  │  │  │  │  │  └────────────────────── tempo=47
│  │  │  │  │  │  └───────────────────────── version 01
│  │  │  │  │  └──────────────────────────── сигнатура EF
│  │  │  │  └─────────────────────────────── сигнатура BE
│  │  │  └────────────────────────────────── length 0x0B = 11
│  │  └───────────────────────────────────── Meta type 0x7F (Sequencer-Specific)
│  └──────────────────────────────────────── Meta prefix 0xFF
└─────────────────────────────────────────── delta 0
```

Обратите внимание:

- **delta = 0** — Meta-событие стоит в самом начале трека.
- **`2F` = 47** — это полу-BPM; итоговый темп = 47 × 2 = **94 BPM**.
- **`03 60` = 480** — `t_time` в 7-битном VLQ: 0x03 × 128 + 0x60 = 480.
- **`04 04 08 04`** — IL=4, ML_A=4, ML_B=8, EL=4.

### 3.3. Что игнорируется

Помимо Meta `FF 7F BE EF`, в первом такте могут присутствовать
стандартные Meta-события:

- **`Meta:TrackName`** — имя трека.
- **`Meta:TimeSig`** — размер такта.
- **`Meta:SetTempo`** — «фактический» темп в микросекундах на четверть.
- **`Meta:KeySig`**, **`Meta:Marker`** — информационные.

**SRA не читает ни одно из них.**  Они безвредны, но и пользы не несут.
Единственное, что реально читается в первом такте, — Meta `FF 7F BE EF`,
описанное в разделе 3.1.

> **Важно: порядок.**  Meta `FF 7F BE EF` должно идти **до** начала
> тела файла.  Обычно оно первое событие в треке (сразу после MThd
> и MTrk-заголовка).  Другие Meta-события могут стоять **до** него —
> `parse_style_header` пропускает все Meta, пока не найдёт наше.
> Но как только начинается тело (первое событие с каналом 0x90–0xEF),
> любое Meta-событие в теле **не допускается** (кроме `EndOfTrack`)
> и приводит к ошибке.

### 3.4. Устаревший формат

Ранее (до v2) параметры кодировались пятью служебными NoteOn-событиями
на канале 1 с нотой 0, где velocity кодировало значение параметра.
Этот формат **больше не поддерживается**: `parse_style_header`
распознаёт только Meta `FF 7F BE EF 01`, а при обнаружении любого
другого первого события тела возвращает `Error(2)`.

Старые стили (созданные для SRA версий до 5.0.0) **не загрузятся**.
Для конвертации из Korg `.STY` используйте отдельный конвертер
`stg2sra` (не входит в этот репозиторий) — он генерирует v2-файлы
напрямую.

## 4. Тело файла (со второго такта)

### 4.1. Порядок секций

Начиная со второго такта (tick = 480 при 120 PPQ и 4/4), музыкальные данные
располагаются в следующем порядке:

```text
Блок 1 (Chord C):
  Intro — IL тактов
  Original — ML_A тактов
  Fill (Orig→Var) — 1 такт
  Variation — ML_B тактов
  Fill (Var→Orig) — 1 такт
  Ending — EL тактов

Блок 2 (Chord Cm): то же самое
Блок 3 (Chord C7): то же самое
```

**Маркеры секций не используются.** SRA определяет границы секций
**арифметически**, отсчитывая такты от начала второго такта, используя
значения IL, ML_A, ML_B, EL из Meta-события первого такта. В полном
дампе `style0.mid` нет ни одного `Meta:Marker` после первого такта —
только NoteOn, ProgChg, PitchBend и EndOfTrack.

### 4.2. Инициализация в начале каждого такта

**Каждый такт** должен начинаться с команд инициализации — Program Change
и/или Bank Select для всех используемых каналов. Без этого SRA вернёт `Error(5)`.

В `style0.mid` в начале **каждого** такта стоят (номера каналов здесь —
0-based, как в файле; в UI SRA они отображаются как 1-based):

```text
ProgChg ch7  pg32 (Acc.Bass)
ProgChg ch8  pg0  (Acc1)
ProgChg ch11 pg49 (Acc3)
ProgChg ch9  pg0  (Drum)
```

Значения **не меняются** от такта к такту — они дублируются.
Это требование SRA, а не художественный приём.

### 4.3. Распределение MIDI-каналов

**В этой версии SRA (форк) файлы стилей должны использовать следующие
каналы** (0-based — как в MIDI-файле; в скобках указан номер для UI):

| Канал (файл) | Канал (UI) | Название | Роль | Патч в style0.mid |
| :--- | :--- | :--- | :--- | :--- |
| 6  | 7  | Acc5 | Аккомпанемент 5 | (не используется) |
| 7  | 8  | Acc.Bass | Автобас | pg32 |
| 8  | 9  | Acc1 | Аккомпанемент 1 | pg0 |
| 9  | 10 | Drum | Ударные | pg0 |
| 10 | 11 | Acc2 | Аккомпанемент 2 | (не используется) |
| 11 | 12 | Acc3 | Аккомпанемент 3 (тянущиеся звуки) | pg49 |
| 12 | 13 | Acc4 | Аккомпанемент 4 (тянущиеся звуки) | (не используется) |
| 15 | 16 | Phrase | Мелодические / фразовые линии | (не используется) |

> **Только эти восемь каналов разрешены в style-файле.**  `sra_load_style`
> проверяет канал **каждого** сообщения в теле файла — не только NoteOn,
> но и NoteOff, Program Change, Control Change, Pitch Bend и любых
> других.  При обнаружении «постороннего» канала возвращается
> `Error(4)`.
>
> **Каналы 6 (UI 7, Acc5) и 15 (UI 16, Phrase)** обрабатываются
> **точно так же, как Acc1–4**: транспонируются по аккорду
> (`chord_v` + `chordd`), velocity умножается на `acc_vf * chord_c`.
> Разница между Acc5 и Phrase — **чисто семантическая**: Phrase
> предназначен для мелодических/фразовых линий (в стиле Yamaha
> PHRASE), Acc5 — для дополнительной гармонической фактуры.
> Транспонирование по гамме (scale-tone) для Phrase-материала при конвертации .STY-файлов
> выполняет **конвертер** (отдельный проект), а не SRA.

**Каналы `M.Bass` (13, UI 14) и `Lower` (14, UI 15)** зарезервированы
SRA для **живой игры** (см. раздел 4.5 ниже): SRA сама генерирует на них
ноты из аккордов, нажатых на клавиатуре.  Эти каналы **не должны**
использоваться в style-файле — события на них вызовут `Error(4)`.


**Каналы 0–5 (UI 1–6)** не используются SRA для аккомпанемента.  Это
каналы для живой игры (мелодия) — SRA читает с них ноты и пробрасывает
их на выход без изменений.  В style-файле их быть не должно.

**Канал 0** дополнительно используется для служебного заголовка первого
такта (пять NoteOn с нотой 0).  В теле файла он не используется.

**Миграция старых файлов.** В оригинальном SRA (ZZ-Denis) раскладка
каналов была другой (Acc.Bass = 1, Acc1 = 4, Acc2 = 5, Acc3 = 6,
Acc4 = 7, Drum = 9), а формат заголовка — старый (NoteOn + velocity).
Файлы из оригинального SRA **не загрузятся в этом форке**:

- `sra_load_style` проверяет каналы по новым константам и вернёт
  `Error(4)` при несовпадении;
- `parse_style_header` ищет Meta `FF 7F BE EF` и вернёт `Error(2)`,
  если её нет (а в старом формате её нет по определению).

**Миграция в этом репозитории не поддерживается.**  Файлы нужно
пересоздать из источника.  Для Korg `.STY` используйте конвертер
`stg2sra` (отдельный проект) — он генерирует v2-файлы напрямую.

> **Примечание.** Каналы `Acc5` (6) и `Phrase` (15) — **новые**,
> в оригинальном SRA их не было.

### 4.4. Running status и структура байтов

**В теле файла** (`sra_dump_sty`, `sra_count_note`) running status
**поддерживается корректно**: если в потоке байт встречается значение
меньше `0x80`, оно интерпретируется как данные для последнего
статус-байта. Это стандартное поведение MIDI. Running status можно
использовать или не использовать — SRA разберётся в обоих случаях.

**В первом такте** running status **не применим**: там находится
Meta-событие `FF 7F 0B BE EF 01 ...`, а Meta-события, в отличие от
канальных, не используют running status.

> **В v2 нет требования к running status в первом такте.**  Это
> отличает новый формат от старого, где параметры кодировались
> служебными NoteOn и running status был обязателен из-за
> побайтового чтения по фиксированным смещениям.

> **Практический вывод.**
>
> - **В первом такте** running status не важен — там Meta.
> - **В теле файла** running status опционален.
> - **Не все DAW экспортируют running status.** Некоторые всегда
>   записывают полные статус-байты — это нормально, SRA разберётся.

### 4.5. Базовая тональность файла стиля

**Файл стиля должен быть написан в тональности C.**  Это **не**
художественное требование, а **техническое**: SRA использует блоки
`Chord C`, `Chord Cm`, `Chord C7` как **шаблоны**, которые затем
**транспонируются** в тональность играемого аккорда.

Как это работает:

1. Ты играешь, например, **F** (фа мажор).
2. SRA определяет корень (F) и тип (major).
3. SRA берёт **блок Chord C** из style-файла.
4. SRA **транспонирует** все ноты этого блока на интервал **от C до F**
   (то есть на +5 полутонов).
5. Результат отправляется в синтезатор.

Аналогично для минора (берётся блок `Chord Cm` и транспонируется
от C до играемого минорного корня) и для доминантсептаккорда
(блок `Chord C7`).

**Что это значит на практике:**

- **Первый блок** должен быть записан так, как если бы ты играл **C**
  (C, E, G, Bb — в зависимости от нужных ступеней).
- **Второй блок** — как если бы ты играл **Cm** (C, Eb, G).
- **Третий блок** — как если бы ты играл **C7** (C, E, G, Bb).

**Неважно, в какой тональности ты слышишь стиль целиком.** Важно только,
что базовая тональность **шаблона** — C (C / Cm / C7). SRA сделает
транспонирование сама.

**Что произойдёт, если написать блок не от C:**

- Ты написал первый блок **от D** (D, F#, A) — то есть «как будто
  играешь D».
- SRA считает, что это «блок для C». Когда ты сыграешь F, SRA
  транспонирует блок от C до F (+5 полутонов).
- Твой D-блок превратится в **A-блок** (D + 5 = A). Зазвучит **A**,
  а не **F**.
- **Аккомпанемент будет в неправильной тональности.**

**Такая же логика используется в других аранжировщиках.** Например,
Yamaha SFF (Style File Format) для клавиатур PSR/Tyros тоже требует,
чтобы стиль был записан в **Source Root** (обычно Cmaj7), и
транспонирует его под текущий аккорд.

**Meta:KeySignature в файле не играет роли** — SRA его не читает
(см. раздел 3.2). Он может содержать `C major` (или что угодно) —
на воспроизведение это не влияет.

### 4.6. PPQ должно быть ровно 120

**PPQ (TimeBase) должен быть ровно 120.**  Это единственное значение,
при котором SRA воспроизводит стиль с правильным темпом.

Любое другое значение (240, 480, 960 и т.д.) приведёт к тому, что
темп будет неверным — обычно заметно медленнее.  SRA не пересчитывает
темп под PPQ, поэтому изменить PPQ после создания файла нельзя.

> **`t_time` теперь хранится в Meta.**  В v2 длина такта — отдельное
> поле (`<tt_hi> <tt_lo>` в Meta `FF 7F BE EF`), а не вычисляется из
> delta первого события тела, как в старом формате.  Это поле — 2-байтовый
> 7-битный VLQ, максимальное значение 16383.  При PPQ = 120 и 4/4
> длина такта 480 тиков, и `t_time × SESSION_MAX = 480 × 32 = 15360`
> укладывается в лимит.  Если PPQ больше, `t_time` тоже растёт, и
> `t_time × SESSION_MAX` может превысить 16383 — тогда стиль не
> загрузится.  Отсюда и требование PPQ = 120.

> **Практическое правило.**  При создании нового проекта в DAW сразу
> установите `TimeBase` = 120 и не меняйте его.  Если вы открываете
> существующий проект, проверьте PPQ перед экспортом: некоторые DAW
> по умолчанию используют 480 или 960.

Оригинальный `style0.mid` из комплекта SRA использовал PPQ = 120.
Тестовый генератор `tools/make_test_style_v2.py` тоже пишет PPQ = 120.

### 4.7. Порядок событий внутри временной группы

Внутри одной временной группы (то есть между двумя событиями с
ненулевой delta) события должны идти в определённом порядке:

1. **Сначала NoteOn / NoteOff** (ноты).
2. **Потом Program Change** (и другие CC, если используются).

Это связано с работой функции `sra_move_com`, которая при загрузке
стиля **перемещает CC и PC в начало временной группы**.  Она ищет их
**после** NoteOn.  Если PC уже стоят в начале группы, `sra_move_com`
может не найти границу и уйти за пределы буфера — это приведёт
к `SIGSEGV`.

**Что это значит для создания стиля:**

- Внутри одной временной группы **первым** должно идти событие NoteOn
  или NoteOff.
- Program Change — **после** нот.
- Если вы пишете стиль вручную, сначала добавляйте ноты, потом PC.
- Если вы конвертируете из Yamaha STY, конвертер должен сортировать
  события так, чтобы ноты шли раньше PC.

**Дополнительно:** перемещение CC/PC в начало временной группы
**не применяется к самой первой группе** файла (до первого ненулевого
delta).  Это нормально — первое событие тела остаётся на своём месте.

> **Первое событие тела может быть любым.**  В v2 `t_time` берётся
> из Meta, а не из delta первого события.  Поэтому требование старого
> формата («первое событие — NoteOn») отменено.  Однако для чистоты
> рекомендуется всё же начинать тело с NoteOn: это упрощает отладку
> и совпадает с примерами (см. `tools/make_test_style_v2.py`).

## 5. Пошаговая инструкция по созданию файла стиля

### Шаг 1: Создание проекта

1. Откройте MIDI-редактор (Cakewalk, FL Studio, Reaper, Anvil Studio и т.п.).
2. Создайте новый проект.
3. **Установите формат SMF Format 0** (в настройках экспорта/сохранения).
4. **Включите running status / «optimize MIDI» / «compress MIDI»** в
   настройках экспорта. Без этого файл не загрузится.
5. **Установите `TimeBase` (PPQ) = 120.**  Это единственное значение,
   при котором SRA воспроизводит стиль с правильным темпом
   (см. раздел 4.6).

### Шаг 2: Первый такт — Meta-событие v2

1. Создайте **одно Sequencer-Specific Meta-событие**
   `FF 7F 0B BE EF 01 <tempo> <beat> <tt_hi> <tt_lo> <il> <ml_a> <ml_b> <el>`
   со значениями:
   - `<tempo>` = половина BPM (67 для 134 BPM), диапазон 10–125
   - `<beat>` = 2, 3, 4 или 6
   - `<tt_hi> <tt_lo>` = длина такта в тиках (обычно `120 × beat`)
   - `<il>` = число тактов вступления, 1–32
   - `<ml_a>` = число тактов Original, 1–32
   - `<ml_b>` = число тактов Variation, 1–32
   - `<el>` = число тактов концовки, 1–32
2. **Meta-событие — на tick 0** (delta = 0).
3. **До Meta `FF 7F BE EF`** могут идти другие Meta-события
   (`TrackName`, `TimeSig`, `SetTempo`) — они пропускаются парсером.
4. **После** Meta сразу начинается тело файла.  Meta-событий в теле
   быть не должно (кроме `EndOfTrack` в самом конце).

> **Обратите внимание:** Meta `FF 7F BE EF` должна быть **единственной**
> в первом такте.  Если она встретится дважды, парсер остановится на
> первой — вторая будет воспринята как начало тела, что приведёт к
> `Error(2)`.

> **Готовый генератор:** `tools/make_test_style_v2.py` — минимальный
> пример v2-стиля.  Используйте его как эталон при отладке.

### Шаг 3: Тело файла

1. Начиная с `tick = 480` (второй такт), запишите музыку в порядке:
   - Intro (IL тактов)
   - Original (ML_A тактов)
   - Fill (1 такт)
   - Variation (ML_B тактов)
   - Fill (1 такт)
   - Ending (EL тактов)
2. Повторите этот блок **три раза** — для C, Cm, C7.
3. **В начале каждого такта** поставьте Program Change для используемых
   каналов (7, 8, 9, 10, 11, 12 — по таблице 4.3), даже если патч не меняется.
4. **Внутри одной временной группы** ставьте ноты раньше PC (см. раздел 4.7).
5. Используйте ноты только на каналах из таблицы 4.3. События на других
   каналах вызовут `Error(4)`.
6. **Пишите музыку в C / Cm / C7** (см. раздел 4.5). SRA сама
   транспонирует блоки под играемый аккорд.
7. **Следите за delta** — она не должна превышать 16383 (см. раздел 4.6).

### Шаг 4: Сохранение

1. Сохраните файл как `style0.mid` (или `style1.mid` … `style127.mid`).
2. Поместите файл в директорию с исполняемым файлом SRA.
3. Проверьте загрузку через SysEx-команду `F0 7D 20 <NN> F7`, где
   `<NN>` — номер стиля. В старых версиях это был Function Mode
   (`Shift+Ab7` + клавиша стиля).

## 6. Типичные ошибки

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `Error(2)` | Не найдено Meta `FF 7F BE EF` в начале трека, или неверная версия (не `01`) | Убедиться, что первое событие — Meta `FF 7F 0B BE EF 01 ...`, сразу после MThd и MTrk-заголовка. Проверить, что файл сохранён как SMF Format 0 |
| `Error(3)` | Параметры в Meta вне диапазона | Проверить: Tempo 10–125, Beat 2/3/4/6, IL/ML_A/ML_B/EL 1–32 |
| `Error(4)` | Недопустимый MIDI-канал в теле файла | Использовать только каналы **6, 7, 8, 9, 10, 11, 12, 15** (0-based): `Acc5`, `Acc.Bass`, `Acc1`, `Drum`, `Acc2`, `Acc3`, `Acc4`, `Phrase`. Каналы `M.Bass` (13) и `Lower` (14) — только для живой игры |
| `Error(5)` | Нет инициализации в начале такта (ProgChg) | Добавить ProgChg в начало каждого такта.  Убедиться, что первое событие тела — NoteOn (рекомендация, не требование) |
| `Error(6)` | Недостаточно тактов | Проверить IL, ML_A, ML_B, EL и фактическое количество тактов |
| `Error(7)` | Файл превышает буфер (лимит 219990 байт) | Сократить стиль или упростить оркестровку |
| `SIGSEGV` в `sra_move_com` | Неверный PPQ (не 120) или PC стоит раньше нот в одной временной группе | Установить PPQ = 120. Убедиться, что PC идут после нот |

## 7. Ключевые нестандартные особенности

1. **Нота 0** на канале 1 — служебная, не музыкальная.
2. **Параметры — в Meta-событии** `FF 7F 0B BE EF 01 ...`
   (Tempo, Beat, t_time, IL, ML_A, ML_B, EL).
3. **Tempo вводится вполовину** — в поле `<tempo>` Meta,
   а не в `Meta:SetTempo`.
4. **`Meta:SetTempo` / `TimeSig` / `Marker` игнорируются** — их можно
   добавлять, можно не добавлять; SRA их не читает.
5. **Нет маркеров секций** — границы определяются арифметически
   по IL/ML_A/ML_B/EL.
6. **ProgChg дублируются в каждом такте** — требование SRA,
   а не изменение инструментов.
7. **Running status в первом такте не применим** — там Meta-событие,
   а не канальные события.  В теле файла running status опционален.
8. **Running status в теле файла опционален** — там работает настоящий
   парсер.
9. **Раскладка каналов в этом форке сдвинута** относительно оригинального
   SRA. Файлы стилей должны использовать каналы 6, 7, 8, 9, 10, 11, 12,
   15 (0-based). Каналы 13 (`M.Bass`) и 14 (`Lower`) — только для живой
   игры. Старые файлы не загружаются: нужен v2-формат и новые каналы.
10. **Базовая тональность файла — C (C / Cm / C7).**  Это шаблон, который
    SRA транспонирует под играемый аккорд.  Если написать блоки в другой
    тональности, аккомпанемент зазвучит неправильно.  Подробнее — в
    разделе 4.5.
11. **PPQ должен быть ровно 120.** SRA не пересчитывает темп под PPQ —
    при другом значении темп будет неверным.  Подробнее — в разделе 4.6.
12. **Порядок событий внутри временной группы важен:** сначала ноты,
    потом PC.  Первое событие тела — NoteOn.  Подробнее — в разделе 4.7.
